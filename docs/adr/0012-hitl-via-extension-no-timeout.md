# HITL gates live inside extensions via per-task `no_timeout`, not as a new `videos.status` value

## Context

The music-video kind (ADR-0011) introduces two operator-blocking gates that the narrative kind does not have. Both require operator action against an external service before the pipeline can continue:

1. **Magnific image selection** — step `generate-loop-image` asks Magnific to produce variations from a prompt, and the operator must pick one. There is no programmatic "best" choice; the variations are visually different and the operator's eye is the only judge.
2. **Suno hCaptcha** — `suno-ext` discovers via `POST /api/c/check` that some generation requests require a captcha token. Ambientforge's Python sidecar solves this via Chrome + CDP at port 9333; an MV3 extension cannot. v1 falls back to operator-manual captcha solving in the operator's signed-in `suno.com` tab.

Both gates are *human-in-the-loop* (HITL) — neither is auto-resuming on a timer (unlike `deferred_until`, which the Google Flow runner uses when all accounts are simultaneously in cooldown and the reaper unblocks once one frees up). The question is where the awaiting-operator state lives.

Two architectural shapes were weighed:

1. **HITL absorbed by the extension.** The HistForge worker step sees a normal task that happens to take longer than usual. The relevant queue row (`magnific_queue` or `suno_queue`) stays `dispatched`; the extension blocks internally (DOM-watching, polling, content-script messaging) until the operator unblocks it. The only HistForge-side accommodation is a per-task no-timeout flag so the reaper does not requeue an HITL task mid-selection.

2. **HISTForge models HITL as a first-class lifecycle state.** A new `videos.status='awaiting_operator'` value. Step writes that status and exits; the extension uploads candidate artifacts (e.g., N Magnific variations) via a new binary-upload webhook; the HistForge dashboard renders a kind-aware UI (a variation gallery for Magnific, a captcha banner for Suno); operator action through HistForge transitions status back to `in_progress`.

The decision criterion is how the operator actually picks variations and how much HistForge-side machinery that supports. The operator's natural workplace for image selection is the Magnific tab where they can zoom, compare, and re-roll if no variation works. The operator's natural workplace for captcha solving is the suno.com tab where they're already authenticated. Forcing the operator into HistForge for selection means HistForge has to render and serve those artifacts (variation thumbnails, captcha widgets) — work that the extension can avoid by keeping the operator in the source UI.

## Decision

1. **HITL state lives on the queue row, not on the `videos` row.** No new `videos.status` value. Both new queue tables — `magnific_queue` and `suno_queue` — carry a `no_timeout INTEGER NOT NULL DEFAULT 0` column. The reaper checks this column before requeueing a `dispatched` task whose age exceeds `dispatch_timeout_minutes`; rows with `no_timeout=1` are exempt.

2. **The operator picks in the source UI, not in HistForge.** Magnific image-pick happens in the operator's Magnific tab; the extension watches the DOM (or injects an overlay button) for the click and harvests the chosen image URL. Suno captcha solving happens in the operator's suno.com tab; a content script reads the solved hCaptcha token after the operator clears the challenge. In both cases, the extension submits the unblocked state to HistForge via the existing `/submit-result/<token>` webhook shape (same as the Google Flow pattern in §12b.2).

3. **HistForge surfaces the awaiting state via a dashboard banner**, not via a status column. The video detail page reads from `magnific_queue` / `suno_queue` and shows a kind-aware banner ("Operator selection needed in Magnific tab" / "Suno captcha needed — solve in your suno.com tab") for as long as the matching queue row is `dispatched` with `no_timeout=1`. The banner is informational; clicking it deeplinks to the relevant tab or focuses the existing one. No HistForge-side widget renders variations or captcha.

4. **The Google Flow reaper's existing two-pass design is extended** with a third predicate: `no_timeout=1` rows are skipped by the dispatch-age requeue pass. The 10-minute account-liveness pass already only fires for rows whose account hasn't been seen — single-account services (`magnific_queue`, `suno_queue`) only need the dispatch-age pass, gated by `no_timeout`.

5. **The `no_timeout` flag is set per-task at enqueue time** based on the task's mode. For `magnific_queue`: `mode='image-hitl'` enqueues with `no_timeout=1`; `mode='image-to-video'` enqueues with `no_timeout=0` (autonomous). For `suno_queue`: enqueue with `no_timeout=0` by default; suno-ext flips the row to `no_timeout=1` via a webhook update when it detects captcha required (`POST /api/c/check` returns required), and flips back to `no_timeout=0` automatically once it has the token and resubmits the request. The flag is reactive, not predictive — we don't know in advance whether a given Suno song will hit a captcha.

## Considered options (rejected)

**New `videos.status='awaiting_operator'` lifecycle state.** Rejected because the awaiting state is per-step, not per-video — a music video with two awaiting moments (image pick, then a Suno captcha mid-batch) would either thrash the status column twice or need a more granular per-step status. The cost of the new status spreads to every queue-aware UI: the queue table's status pill, the FIFO picker's eligibility (HITL videos still take up the worker's single in-progress slot, so excluding them from `findInProgressId` would be wrong; including them with a new status would force every status-check site to add the new case), the retry/restart flows, the delete-requested flag's interaction with the new status, and the dashboard list polling. Per ADR-0007, the lifecycle module pattern aims to centralize state transitions; adding a status earns its keep only when transitions to/from it carry real composed-write logic. HITL has no such logic — the awaiting state is just "task is dispatched, operator hasn't clicked yet," which the queue row already encodes.

**Binary upload of N candidate images from `magnific-ext` to HistForge for in-dashboard variation selection.** Rejected because (a) it duplicates Magnific's own variation grid (which the operator is going to scroll through anyway during selection), (b) it adds a new binary-upload webhook with non-trivial size handling (a 4-variation batch of Magnific images is ~10-20 MB), (c) it forces HistForge to re-host artifacts that already live on Magnific's CDN, and (d) it splits the operator's attention between two UIs for one task. The operator's "open Magnific tab → click variation → done" loop is shorter and uses the UI Magnific has already optimised for this exact action.

**Reaper just skips all queue tables with single-account semantics.** Rejected because some `magnific_queue` modes (e.g., `image-to-video`) are NOT HITL and *should* have a dispatch timeout to catch silent extension hangs. Per-task `no_timeout` keeps the reaper protective on autonomous tasks while exempting only the HITL ones.

**Operator-set global `awaiting_operator` settings flag** (similar to `google_flow_relogin_needed`). Rejected because that flag is fleet-level — one setting holds the whole queue from advancing on the affected provider until cleared. HITL is per-task: a different video's `image-to-video` task on the same Magnific account can run in parallel with one stuck in HITL on this video. Per-task no_timeout preserves that.

**2captcha / CapSolver for Suno hCaptcha** (avoids HITL entirely). Rejected for v1 per the `project_recaptcha_solver_injection_dead` memory: cross-session token injection was empirically rejected by `aisandbox-pa` with HTTP 403 (Google Flow side). Suno's anti-bot may behave differently — they're a different vendor — but the cost-of-failure asymmetry (paying for a remote service that gets rejected vs. asking the operator to solve manually a few times a session) favors HITL in v1. Revisit as a v2 experiment if operator-interrupt frequency proves painful.

## Consequences

- **Two new queue tables** clone the `google_flow_queue` shape with the additions documented in ADR-0011 and this ADR. `magnific_queue` columns: `id`, `video_id`, `mode` (`image-hitl` | `image-to-video`), `prompt`, `reference_image`, `output_path`, `status`, `no_timeout`, `external_task_id`, `result_url`, `error_reason`, `retry_count`, `created_at`, `dispatched_at`, `completed_at`. `suno_queue` columns: `id`, `video_id`, `song_index`, `style_prompt`, `mode` (`description` for v1), `output_path`, `status`, `no_timeout`, `external_task_id`, `result_url`, `error_reason`, `retry_count`, `created_at`, `dispatched_at`, `completed_at`, plus `UNIQUE INDEX (video_id, song_index)`. Neither has `assigned_account_id`, `paused_until`, or `priority` — single-account semantics for both providers in v1.
- **Six new webhook routes** mirror `/api/flow/*`: `/api/magnific/next-task/[token]`, `/api/magnific/submit-result/[token]`, `/api/magnific/status/[token]`, `/api/magnific/queue-summary/[videoId]`, `/api/suno/next-task/[token]`, `/api/suno/submit-result/[token]`, `/api/suno/status/[token]`, `/api/suno/queue-summary/[videoId]`. The `/status/[token]` endpoint for suno-ext also accepts a `captcha_required` event that flips the in-flight task's `no_timeout=1`; the matching `captcha_cleared` event flips back to `no_timeout=0` before resubmission.
- **The reaper gains one predicate**: `WHERE no_timeout = 0` on the dispatch-age requeue pass. Single-line change in `src/worker/reaper.ts` (the existing Google Flow reaper's logic generalizes; only the per-table query gains the predicate). The 10-minute account-liveness pass is N/A for these single-account tables.
- **Dashboard banners are per-tab + per-video**, not global. The music-videos tab's video detail page reads from `magnific_queue` and `suno_queue` (via `/api/magnific/queue-summary/[videoId]` and `/api/suno/queue-summary/[videoId]`) and renders the awaiting-operator banner when any queue row for that video has `status='dispatched' AND no_timeout=1`. The banner clears as soon as the row transitions to `done`.
- **CONTEXT.md gains a "HITL gate" term** (under "Music video language") naming the per-task no_timeout convention and explicitly flagging that no new `videos.status` value is introduced.
- **No reaper-clock interaction with `videos.deferred_until`.** Defer is auto-resuming, HITL is not. The two mechanisms coexist on different rows: a Google Flow video can be deferred (auto-resumes when an account frees), while a music video can be HITL-blocked (resumes only on operator click). Both can be true on different videos at the same time; neither blocks the other.
- **If a third HITL-requiring provider is added later** (e.g., a paid image-gen service with mandatory operator review), it inherits the same shape: a per-provider queue table with `no_timeout`, the reaper skip predicate, a dashboard banner. The pattern is open-ended.
- **The cost of "operator forgot to click for hours"** is a stuck `dispatched` row that won't get reaped. Mitigation: the dashboard banner is the nudge, and the existing `delete_requested=1` flow handles abandonment (the orchestrator's between-step delete check fires once the operator gives up and deletes the video).
- **The cost of switching to HistForge-side variation review later** is recoverable: add the `awaiting_operator` status value, add a binary-upload webhook, add the variation gallery component on the detail page. The data already flows through HistForge in submit-result; we'd just rotate which side of the network owns the operator interaction. The `no_timeout` column does not become wasteful in that future — it still gates the reaper for autonomous-mode tasks; it just stops being the *primary* HITL signal.
