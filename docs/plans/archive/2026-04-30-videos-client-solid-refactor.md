# SOLID refactor of videos-client.tsx (list page)

## Overview
Apply the three findings from `docs/refactoring/solid-audit-2026-04-30-videos-client.md` to `src/app/videos/videos-client.tsx`, in the order the audit prioritises. Extract the failure-banner subsystem first (the cleanest mechanical move, ~95 lines), then collapse the duplicated action handlers behind one helper, then lift the polling effect plus row-split policy into a `useVideoPoller` hook. End state: the orchestrator drops from 456 lines to ~165 and its only remaining job is layout composition + modal/dialog state + row-action busy state.

## Current State

**File under refactor**
- `src/app/videos/videos-client.tsx` — 456 lines as of HEAD. Mixes five concerns: the failure-banner subsystem (lines 38-66 type+parser, 111-112 state, 235-250 dismiss handler, 271 derived value, 286-331 banner JSX), six action handlers totalling ~92 lines (173-269), the polling effect with status-diff toast emission (121-169), the row-split policy (70-91), and the modal/dialog state (116-119, 438-452). The audit cites ~165 lines as the target after all three findings land — line 9 of the audit walks through the arithmetic.

**Pattern to mirror — siblings**
- `src/app/videos/[id]/flow-moderation-panel.tsx`, `flow-progress-panel.tsx`, `flow-accounts-strip.tsx` — `"use client"` siblings with typed props interface above the component, named export, `: JSX.Element` return-type annotation. The video-detail directory just absorbed the same kind of extraction (see `docs/plans/2026-04-30-video-detail-client-modular-split.md`); shape and conventions are settled.
- `src/app/videos/_shared.tsx` — module of small presentational helpers (`StatusBadge`, `SectionHeading`, `QueueStatusPill`) consumed across the videos surface. The orchestrator already imports `SectionHeading` and `QueueStatusPill` from this module; both stay. The new banner sibling lives at the videos-list directory root rather than under `_shared.tsx` because it owns busy state plus a network call.

**Hook-naming precedent**
- `src/app/settings/google-flow-accounts-hooks.ts` is the project's only existing custom-hook module; it uses a `<topic>-hooks.ts` filename and bundles multiple hooks. Single-hook files in this plan use `use-<name>.ts` (more common React convention). The implementer may rename if they prefer to match the existing project precedent — function-name and call-site behaviour matter, file name is a soft choice.

**Tests in scope**
- `__tests__/components/videos/videos-client.test.tsx` (348 lines, **15 tests**). Coverage map: layout headings + Add-Topic modal + Start-All disabled/enabled/POST (lines 104-172, 5 cases); queue pause/resume header rendering and POST routes (174-226, 4 cases); flow_create_project_failed banner across empty / valid JSON / malformed JSON / mid-session-polling / Dismiss-POST cases (228-321, 5 cases); polling-driven status transitions and toasts (323-348, 1 case). Every assertion targets rendered output, recorded fetch calls, or toast mock calls — never internal component identity — so the refactor must keep DOM, fetch wire shape, and toast behaviour identical. Task 0 records the green baseline before any extraction begins.

**Convention to honour in new files**
- `"use client"` directive at the top of any new file that uses React hooks or imports client-only helpers.
- `: JSX.Element` return-type annotation on the public component (or an explicit return type on a hook).
- Typed props interface above the component for sibling components — see `src/app/videos/[id]/flow-progress-panel.tsx:15-22`.

## Scope

**Doing**
- Extract `flow-failure-banner.tsx` (Finding #1). Owns the type, parser, banner JSX, busy state, and dismiss handler. Takes the raw setting string from the orchestrator; reports back via an `onCleared` callback when the dismiss POST succeeds.
- Centralise the remaining five action handlers behind one helper (Finding #2). Each call site declares its post-success pattern (`router.refresh()` vs local-state setter) and its error-toast policy (message string vs explicit silence) at source.
- Extract `useVideoPoller` hook (Finding #3). Owns `splitRows`, `QUEUE_STATUSES`, `POLL_MS`, the polling `setInterval`, the `prevStatuses` ref, and the status-diff toast emission. Returns `{ topics, queue, finished, queueState, setQueueState, flowCreateProjectFailed, setFlowCreateProjectFailed }` so the orchestrator can still flip `queueState` from the queue-toggle action and clear `flowCreateProjectFailed` from the banner's `onCleared` callback.
- Keep `VideosClientProps` byte-identical so `src/app/videos/page.tsx` is not touched.

**Not doing**
- A dedicated unit-test file for the parser. The existing `videos-client.test.tsx` already exercises the empty / valid / malformed JSON branches at rendered-output level (228-265); a separate suite would duplicate coverage. If the parser later grows new branches, add a unit test then.
- Any change to the API list route's bucket policy — the audit explicitly notes "de-duping that is out of scope here" (line 41 of the audit).
- Sharing `useVideoPoller` with `video-detail-client.tsx`. The two pages poll different payloads; convergence is a future cross-cutting concern, not scope for this plan (audit's Notes section, line 66, calls this out as optional).
- Lifting modal/dialog state (lines 116-119, 438-452) out of the orchestrator. Audit Finding #3 explicitly leaves modal/dialog state at the orchestrator level.
- Lifting the three section layouts (Topics, Queue, Finished `<section>` blocks at 333-436) into separate components. The audit explicitly says they "stay inline — each is ~30 lines and reads as a layout, not as logic" (line 40 of the audit).
- Migrating `RowInflight`'s discriminated-union shape. The audit's Notes section (line 64) calls it "the right shape" and a "positive pattern worth keeping."
- Renaming or restructuring the directory (no `_components/` subfolder, no move under `_shared.tsx`). The directory uses flat sibling files (`topics-table.tsx`, `add-video-modal.tsx`, …); the new files follow suit.

### Phase 2: Centralise action handlers (audit Finding #2)

- [x] **Task 2: Introduce shared action helper and migrate the five remaining handlers**
  _Landed_: helper owns `useRouter()` internally; orchestrator's `useRouter` import dropped. Task 4(c)'s lint sweep should expect that drop. `BusyHandle` is exported from `use-video-action.ts` so row handlers can shape `setRowInflight` into the helper's contract while `RowInflight` survives intact (per audit Note line 64).
  **Files**: `src/app/videos/use-video-action.ts` (new — `.ts` extension since the helper exports a hook with no JSX), `src/app/videos/videos-client.tsx`
  **What**: Add a hook (or equivalent helper — name and exact signature are an implementation choice, but the constraints below are required) that the five remaining handlers (`onStartAll` 173-184, `onStartVideo` 186-197, `onPauseVideo` 199-215, `onResumeVideo` 217-233, `onToggleQueue` 252-269) call. Required constraints:
  - **Each call site declares its post-success pattern explicitly.** The two patterns the file uses today are (a) "let the next poll refresh state" — the four video-row handlers call `router.refresh()`, which is best-effort because client `useState` initial values aren't re-derived from changed props; the eventual UI update lands via the next 5 s poll cycle; (b) "set local scalar state synchronously" — `onToggleQueue` flips `queueState` directly so the user sees the pause/resume change without waiting up to 5 s. The helper must surface both as named choices (e.g. `onSuccess: "router-refresh"` vs `onSuccess: (res) => setQueueState(...)`); a default that's silently overrideable is not acceptable because the audit's specific complaint (lines 32-33 of the audit) is that the choice is implicit today and a reader can't tell whether the pattern is intentional or accidental.
  - **Error-toast policy is explicit per call site.** Today `onStartAll` and `onStartVideo` swallow non-OK responses with no toast, while the three remaining handlers toast a default-or-server message. The helper must accept an explicit silent-failure flag (e.g. `errorToast: false` or `errorToast: { message: "Failed to ..." }`) so each call site declares the silent-failure decision in source, with a one-line comment justifying it where used. Per audit line 33: "that's an inconsistency that shouldn't be hidden behind copy-paste."
  - **`RowInflight` survives intact.** The audit's Notes section (line 64) calls `RowInflight` "the right shape — one piece of state for 'which row is doing what,' not five booleans." The three row-action handlers (`onStartVideo`, `onPauseVideo`, `onResumeVideo`) continue to write through `setRowInflight` for their busy state; do not collapse those into per-handler booleans. The two scalar-action handlers (`onStartAll`, `onToggleQueue`) may either (a) keep their current `startingAll` / `togglingQueue` booleans in the orchestrator and have the helper write through them, or (b) have the helper own a hook-internal busy flag and return it. Either is acceptable; the implementer should pick whichever produces the cleaner call site. Net delete from the orchestrator for Task 2 alone is ~75 lines per audit Finding #2 body (line 33), bumping toward ~85 if choice (b) collapses the two scalar booleans into helper-internal state. The audit summary's ~105 figure (line 9) bundles in cleanup attributed to Finding #1's `dismissingBanner` and is not a Task 2 target.
  - **Wire shape stays byte-identical.** Path, method, body, and response interpretation are unchanged for every existing handler. The defensive `(await res.json().catch(() => ({}))) as { message?: string }` parse used for the two row-mutation toasts (207-211, 225-229) collapses into the helper.
  - **The helper lives in this directory.** Not under `lib/`, because its constraints are coupled to this page (the two-pattern post-success choice, the `RowInflight` interplay, the shape of the toast messages).
  - **`useRouter` ownership is an implementation choice.** Either the orchestrator continues to call `useRouter()` and passes the router (or a `refresh` callback) into the helper, or the helper calls `useRouter()` internally. Both keep the `useRouter` mock at test lines 18-20 working. The choice determines whether the orchestrator's `useRouter` import survives — call this out in the Task 2 PR description so Task 4(c)'s lint sweep has the expected outcome documented.
  **Context**: `dismissingBanner` and `onDismissBanner` are out of scope here — they moved into `flow-failure-banner.tsx` in Task 1 and the banner has its own internal busy state. Behaviour pin: the `videos-client.test.tsx` cases at 147-225 (POST URLs and methods for Start-All, Pause-Queue, Start-Queue) must pass unchanged — every assertion checks the URL/method on the recorded fetch call, so any drift surfaces immediately. The `useRouter` mock at 18-20 keeps working under either ownership choice above.
